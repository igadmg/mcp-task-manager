Steps
1. Update `Index.NextID()` so it still calls `idx.syncIfStale()` and still considers in-memory active index entries, but also accounts for `MarkdownStorage.NextID()` so archived IDs are not reused.
2. Preserve the `Index.NextID() int` signature. If `idx.storage.NextID()` returns an error, fall back to the current in-memory calculation instead of changing callers or surfacing a new error.
3. Do not rebuild the active index from archived tasks and do not add archived tasks to `idx.entries`; archived tasks remain accessible only through archive storage APIs.
4. Extend `TestIndex_NextID` or add a focused adjacent test to cover:
   - no active index entries, archived task ID `78`, expecting `79`;
   - active index entry ID `12` plus archived task ID `78`, expecting `79` because the highest ID is archived;
   - active index entry ID `90` plus archived task ID `78`, expecting `91` because the highest ID is active.
5. Keep existing ordering and stale-index tests unchanged, including `TestIndex_AutoRebuildsWhenDiskHasNewTasks`.

Code guidance
- Compute the active max exactly as the current loop does.
- Convert the active max to `activeNextID := activeMaxID + 1`.
- Ask storage for `storageNextID, err := idx.storage.NextID()`.
- Return the greater of `activeNextID` and `storageNextID` when there is no storage error; return `activeNextID` if storage scanning fails.
- This max operation is important because `idx.entries` can include unsaved in-memory tasks after `idx.Set()` and before persistence, while `storage.NextID()` sees active/archive files on disk.
